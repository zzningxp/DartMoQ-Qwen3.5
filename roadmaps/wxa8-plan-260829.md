# WxA8 路线规划（2026-08-29）

> WxA16 阶段已进入维护态（混合 bit 权重 + fp16 激活 + fp16 Tensor Core 计算）。
> 本文件规划 **WxA8** 新路线：激活量化为 INT8，矩阵运算走 INT8 Tensor Core（INT32 累加），
> 反量化回 FP16 后做非线性。目标：在 ppl 可控前提下进一步提升推理速度。

---

## 一、技术方案

### 数据流（一层 MoE 为例）

```
上一层输出 (FP16)
    ↓
[分组旋转]  per-group QR 正交旋转（group_size=128，每 group 独立 seed）
    ↓                                      ← 已有，WxA16 也做这一步
[激活量化]  per-token per-group 对称量化 → INT8 + scale
    ↓                                      ← 必须在旋转之后
[矩阵乘法]  INT8 激活 × INT8 权重（码本查表到 INT8）→ INT32 累加（group 内）
    ↓
[反量化]   INT32 × act_scale[b,g]（已含 cb_step） × norms_gf[n,g] → FP32 累加 → FP16
    ↓
[非线性]    SiLU / MoE gate 等（FP16）
    ↓
[下一层]
```

### 核心要点

- **A8 = 参与矩阵运算的激活输入是 8-bit**（不是输出 8-bit，也不是激活函数 8-bit）
- 矩阵乘累加器 group 内是 **INT32**，出 group 转 FP32 总累加
  （现有 WxA16 是 fp16 累加，所以 WxA8 在累加侧是**精度升级**）
- 反量化后回到 **FP16**，所有非线性、归一化、路由都在 FP16 下做
- 权重仍然是混合 bit（1/2/4bit），kernel 内 unpack 后查 **INT8 码本**
- Triton 原生支持 `tl.dot(int8, int8, out_dtype=int32)`，
  **sm120 + Triton 3.5.0 实测走通**（见 §四）
- ⚠ **激活量化必须在分组旋转之后**，且 gate_up / down 的旋转不同，
  不存在"在 MoE 入口一次量化两边共用"

### 为什么是 WxA8（先不做 WxA4）

| 维度 | WxA8 | WxA4（int4 计算） |
|---|---|---|
| Triton 支持 | ✅ `tl.dot(int8,int8) → int32` 成熟（sm120 实测走通） | ❌ 无 WGMMA int4，需外部库或 inline PTX |
| 理论吞吐 | **2x FP16**（SM120 dense：FP16 419 TFLOPS / INT8 838 TOPS） | ~4x FP16（SM120） |
| ppl 退化 | 小（激活量化实测 relerr 0.65%） | 中（0.5-1.0 ppl，需更精细量化策略） |
| 工程难度 | 低-中（融合 kernel 已跑通，见 §四） | 高（20-40 人天，Machete 库或 CUTLASS） |
| 基础设施复用 | 高（量化框架、MoE 调度全部复用） | 中（需要重新处理 int4 packing） |

> ⚠ 修正：初版本表写的"WxA8 ~4x / WxA4 ~8x FP16"是错的。SM120 上
> INT8 是 FP16 的 **2x**（不是 4x），FP4 才是 4x。而且实测这些形状下裸
> `tl.dot` 只跑到 194 TFLOP/s（fp16 峰值 419），本来就没吃满 MMA，
> 所以 WxA8 的收益主要来自**输入 tile 访存减半**，不是 MMA 变快。

**结论**：WxA8 是最务实的下一步。Triton 原生支持，工程可控，精度风险低。
等 WxA8 跑通验证后，再考虑 WxA4（上 Machete 库或 CUTLASS）。

## 二、量化方案

### 激活量化

- **方式**：per-token **per-group** 对称量化（group 粒度 = 权重量化的 group_size = 128）
- **公式**：`x_int8 = round(x_rot / scale)`，`scale = max(abs(x_rot)) / 127`（按 group 取 max）
- **为什么是 per-group 而不是 per-token 整行**：激活进 kernel 前已按 group
  分别做过**独立的 QR 旋转**（每个 group 一个旋转矩阵，seed = seed_base + g_start），
  各 group 幅度不同；per-group scale 让每个 group 都吃满 int8 的 127 级。
  而且现有 kernel epilogue 本来就逐 group 乘 norm，加一个逐 group 的激活
  scale 不增加结构复杂度。
- **计算位置**：⚠ **必须在分组旋转之后**，不是"MoE forward 入口"。
  旋转是正交变换但按 group 独立进行，会改变每个 group 的幅度分布，
  scale 必须在旋转后的值上算。
  而且 **gate_up 和 down 用的是不同旋转**
  （down 的 seed 还带 expert 偏移，见 `triton_kernels.py:1306`），
  K 空间也不同（2048 vs 512）——**不存在"在 MoE 入口一次量化两边共用"的可能**。
  正确落点：
  - gate_up：融进 `_build_hoisted_rotations`（`bit_partitioned_moe.py:526`），
    每个 bit 旋转+量化一次，per-expert 只切片。顺带让 `gather_rotated`
    的字节数减半。
  - down：旋转 seed 依赖 expert，只能逐 expert 在 `batch_rotate_input` 之后量化。
- **实测精度**：per-group int8 的相对误差 0.65%（高斯下的理论值也是 0.66%），
  与 tile 配置无关。

### 权重量化

- 权重仍然是**混合 bit 分组量化**格式（与 WxA16 相同的 packing 方式）
- Kernel 内部：权重 unpack → 查 **INT8 码本**（而不是 fp16 码本）
- 码本转 INT8：`cb_i8 = round(codebook / max|codebook| * 127)`，
  把 `cb_step = max|codebook|/127` **折进激活 scale**（不是 norms）——
  这样 `norms_gf` 与 WxA16 共用同一份 fp16 buffer，零额外显存，
  也避免把 norms 乘小到 fp16 次正规区
- **低 bit 下这一步代价很小，现有 2bpw checkpoint 直接可用、无需重新量化**：

  | bit | 总 relerr | 码本额外贡献 |
  |---|---|---|
  | 1 | 0.00647 | ≈ 0 |
  | 2 | 0.00651 | ≈ 0 |
  | 4 | 0.00860 | ≈ 0.0056 |
  | **8** | **0.0128** | **≈ 0.011 ⚠** |

- ⚠ **8-bit 是例外，这是初版计划漏掉的风险**：8-bit 码本是 256 级
  **Lloyd-Max（非均匀，零点附近极密）**，映射到均匀的 int8 网格时零点附近
  多级会塌成同一个值，等效把 W8 降成约 **W6**。attention 当初正是因为敏感
  才留 8-bit，所以 attention 路径要走 WxA8 **必须先把 8-bit 量化改成
  均匀对称码本**（高码率下均匀 vs Lloyd-Max 的 MSE 差距 < 0.25 dB，
  精度上基本免费，但需要重新量化 attention —— MoE 不受影响）。

### 反量化（矩阵乘后）

- `out_fp16 = out_int32 * act_scale[b,g] * norms_gf[n,g]`
  其中 `act_scale = amax/127 * cb_step`（旋转后按 group 取 max，见上），
  `norms_gf = norms / sqrt(group_size)`（与 WxA16 完全同一份 buffer）
- **两个 scale 都是 per-group 的，正好落在内层 dot 之外** —— 现有 WxA16
  kernel 本来就是 `total_acc += acc_g * norm_g`，把激活 scale 塞进同一个
  epilogue 即可，**数据流结构一行都不用改**。这是 WxA8 工程量远低于
  预估的根本原因。
- 累加器：group 内 INT32，出 group 转 FP32 总累加。
  注意现有 WxA16 是 **fp16 累加**（`out_dtype=tl.float16`），
  所以 WxA8 在累加侧其实是**精度升级**。

## 四、实测结果（2026-08-29 ~ 08-30，RTX 5090 / SM120 / Triton 3.5.0）

形状取自真实 eval（per-expert B = T×top_k/num_experts = 65536×8/256 = 2048）：
gate_up N=1024 K=2048，down N=2048 K=512，group_size=128。

### 融合 kernel 加速比（vs WxA16 同形状）

| 方向 | bit | WxA16 | WxA8 | 加速比 |
|---|---|---|---|---|
| gate_up | 1 | 65.1 us | 40.7 us | **1.60x** |
| gate_up | 2 | 71.1 us | 44.2 us | **1.61x** |
| gate_up | 4 | 103.2 us | 58.0 us | **1.78x** |
| down | 1 | 34.8 us | 25.9 us | 1.35x |
| down | 2 | 38.9 us | 28.0 us | **1.39x** |
| down | 4 | 55.3 us | 33.1 us | 1.67x |

bit=2 主力场景两个 kernel 合计 **109.9 → 72.2 us（1.52x）**。
按 backlog:207-215 的 CUDA event 口径（kernel 占 MoE forward 约 66%），
当时预期 MoE 层省约 23%；**实际端到端测出 MoE wall 省 10.6~11.1%**
（见下方「端到端实测」）—— 差距的原因是 kernel 只占 MoE wall 的约 20%，
详见端到端实测的注意点 3。

### INT8 的最优 tile 与 WxA16 完全不同 —— 必须单独调

沿用 WxA16 的配置只有 1.24x，重调后是 1.61x，**差 20%**：

| | WxA16 最优 | WxA8 最优 |
|---|---|---|
| gate_up large | (64, 128, 32, w4, s4) | **(256, 32, 128, w4, s2)** |
| down large | (64, 128, 128, w4, s2) | **(256, 32, 128, w4, s2)** |

规律：BLOCK_K=128（= group_size，内层只跑一次）与 BLOCK_N=32 全场景最优。
INT8 权重 tile 加载便宜，N 切窄换来更大的 BLOCK_B 更划算。

### B 盈亏交叉点与分派否决

盈亏交叉点在 **B ≈ 256**（更细的扫描见下表）：

| B | 8 | 32 | 64 | 128 | 256 | 1024 | 2048 |
|---|---|---|---|---|---|---|---|
| gate_up | 0.89x | 0.94x | 0.96x | 1.00x | 1.05x | 1.78x | 1.60x |
| down | 0.92x | 0.96x | 1.00x | 1.04x | 1.07x | 1.38x | 1.38x |

小 B 下 kernel 远没吃满（B=128 时填充仅 37.6%，0.38 波），INT8 省下的
访存与 MMA 换不回多加载两组 scale 的成本。

**但 B 自适应分派最终被否决**：小 B 区间的绝对损失最多 2.8us/调用
（B=8 时 gate_up），而大 B 能省 26.6us；为小 B 维护 fp16 缓冲
（每 bit 约 128MB）或逐 expert 重算旋转（额外 launch ~5us）都比
直接吃掉那 ≤2.8us 更亏 → **MoE 模块无条件走 A8**。
`WXA8_MIN_B=256` / `wxa8_is_profitable()` 保留给独立调用场景
（同时持有 fp16 与 int8 两份激活时）。

### 顺带发现的 WxA16 问题（不属于 WxA8，另记）

WxA16 在 B=256→384 处有性能悬崖：25.7 us → 59.3 us（工作量只多 1.5x，
耗时涨 2.3x）。原因是 `_B_THRESHOLD_SMALL=256` 一过就切到 large 档配置
(64,128,32,w4,s4)，而该配置在中等 B（384~1024）区间明显不合适。
**这是 WxA16 侧一个独立的优化机会**，建议补一档 "medium" 配置。

### GPU 填充度

| 场景 | grid | 波次 | 整体填充 |
|---|---|---|---|
| gate_up B=2048 | 256 CTAs | 1.51 | 75.3%（尾波仅 51%） |
| down B=2048 | 512 CTAs | 3.01 | 75.3% |

gate_up 的 1.51 波是个短板 —— 尾波只用了一半 SM。但配置扫描显示
256-CTA 的配置仍是最快的，说明当前受限于单 CTA 内的效率而非并行度。

### rotate+quantize 融合 kernel（P2 补充实测）

两段式（bmm 旋转 + 单独量化扫一遍）在真实规模下量化那遍是主体开销
（hoist B=65536：bmm 1.14ms，量化单独 4.09ms），且要过一遍 fp32 中间态。
融合后旋转结果全部留在寄存器，x 只读写各一趟：

| 场景 | 两段式 | 融合 | 加速比 |
|---|---|---|---|
| gate_up hoist B=65536 G=16 | 5.23 ms | **0.28 ms** | **18.75x** |
| down per-expert B=2048 G=4 | 0.06 ms | 0.01 ms | 4.57x |
| down 小 expert B=512 G=4 | 0.06 ms | 0.01 ms | 4.52x |

数值：与两段式逐元素对拍 maxd=1（int8 取整粒度内），scale relerr 8e-4
（fp16 存储精度）。融合 kernel 与 `batch_rotate_input` 的旋转约定完全一致
（`x @ P^T`），旋转矩阵直接复用 `generate_batch_rotation_matrices` 的缓存。

实现要点（容易写错的地方，都犯过并修了）：
1. **旋转方向**：必须算 `x @ P^T`（`acc = dot(x_tile, trans(p_tile))`），
   用 `x @ P` 时 scale 会凑巧接近（max 分布相似）而数值全错 —— 这种错
   单看 relerr 会骗过对拍
2. **cb_step 只折进存出的 scale**：量化除法 `q = round(acc / scale_unf)`
   必须用未折的 `amax/127`，折进去会把 q 全体放大 cb_step⁻¹ 倍再被
   clamp 饱和成 ±127
3. **BLOCK_B 不能缩块**：`tl.dot` 要求 M ≥ 16，极小 expert（B<16）靠
   mask 丢掉多余行，不动态缩 BLOCK_B
4. **模块级：down 输出要 cast 回原激活 dtype**（接线阶段踩到）：
   WxA8 wrapper 固定产出 fp16，而真实模型激活是 bf16 —— 不 cast 的话
   `index_add_` 直接 dtype 不匹配报错（合成测试的 fp32 输入先暴露了它，
   真实模型上必炸）。cast 对齐 WxA16 wrapper 的既有语义。

### 端到端实测（2026-08-30，sequential eval，同一台机器同一 log 内四组对照）

| 数据集 | WxA16 | WxA8 | ppl Δ | 端到端时间 Δ |
|---|---|---|---|---|
| wikitext2 | 7.7944 @ 58.18s | 7.7975 @ 54.09s | **+0.0031** | **-7.0%** |
| c4 | 11.2680 @ 88.62s | 11.2717 @ 82.71s | **+0.0037** | **-6.7%** |

ppl 退化几乎为零（计划预估 0.1~0.3，实测好一个数量级）——
旋转对离群值的抑制 + per-group 量化按设计工作。

forward 内部拆分（Global Stats）：

| 运行 | forward | moe | attn |
|---|---|---|---|
| WxA16 wiki | 37.97s | 32.33s | 6.97s |
| WxA8 wiki | **34.60s** | **28.74s（-11.1%）** | 6.90s |
| WxA16 c4 | 65.16s | 60.45s | 5.51s |
| WxA8 c4 | **59.17s** | **54.02s（-10.6%）** | 5.97s |

两个注意点：
1. **第一次 WxA8 跑会被 JIT 编译污染**（wiki 首次 62.68s，重跑 54.09s；
   逐层曲线前 5 层/后 5 层 = 1.49 vs 干净的 1.09，且未改动的 attn 也慢 16%）。
   测量前必须先跑一次任何 wxa8 eval 把 Triton 磁盘缓存捂热。
2. **sequential eval 工作流下 MoE 占 forward 约 83%，attention 只有约 10%**。
   这与 backlog 里"attention 32% / MoE 15%"的 GPU 口径（batch eval 测量）
   完全不同 —— 在用户的实际工作流里 MoE 才是绝对大头。
   P3（attention A8）的收益上限因此要按 ~10% 的占比重估（约 3%）。
3. **下一个大杠杆在 per-expert 循环，不在 kernel 本体**（计时口径已核实：
   层级 `moe` = 每层全部 batch 的 mlp.forward wall 之和，wiki 7 批/层、
   c4 13 批/层）。模块内部单次 forward 的 wall 0.118s 里 triton 只有
   0.023s —— **约 80% 是 256 个 expert 的 Python 循环**（gather / 旋转量化 /
   launch / silu / scatter 的串行开销）。kernel 再快也挪不动这 80%。
   方向：P5-2 的多 expert 合并 grouped kernel（`moe_gate_up_grouped_gf`
   等已存在但未并入 main）值得在 rotation hoist + int8 的新前提下重评。

### 收益预期 vs 实测

开工前按 backlog 的 GPU 时间口径（attention 32% / MoE 15%）预估：
只做 MoE 端到端约 **3%**，加上 attention 约 **5~6%**。

**实测（sequential eval，用户实际工作流）好于预估：端到端 -7.0% / -6.7%**，
原因是该工作流下 MoE 占 forward wall 约 83%（不是 GPU 口径的 15%）。
教训：**时间口径决定预期**——GPU 事件口径与 wall-clock 口径给出的
attention/MoE 占比可以差 5 倍以上，评估任何优化的端到端收益前先确认
目标工作流用哪个口径。

相应地，P3（attention A8）在该工作流下的收益上限从预估的 ~3% 缩到
**~2%（attention 只占 forward wall 10%）**，而 **per-expert 循环**
（MoE wall 的 80%）成为更大的杠杆。

## 六、关键风险

1. ~~**ppl 退化超预期**~~ → ✅ 已消除：真实 ppl 实测 wiki +0.0031 / c4 +0.0037，
   几乎为零退化（计划预估 0.1~0.3，实测好一个数量级）。旋转对离群值的抑制
   （等价 QuaRot 思路）+ per-group int8（relerr 0.65%）按设计工作。
2. **8-bit 码本转 int8 有损**（🆕 P1 新发现，初版漏掉）：
   256 级 Lloyd-Max 非均匀码本塞进均匀 int8 网格，等效 W8 → W6，
   relerr 0.00075 → 0.0128。**不影响已完成的 MoE 路径**（低 bit 无损）。
   - 缓解：attention 的 8-bit 改用均匀对称码本（需重量化 attention，MoE 不受影响）
3. ~~**性能不达预期：小矩阵吃不满 INT8 Tensor Core**~~ → 已实测确认存在
   （B<256 时 A8 慢 0.89x~1.03x），但**分派方案被否决**：小 B 绝对损失
   ≤2.8us，双缓冲/重算旋转的成本比这更大 → 无条件走 A8（见 §四）
4. **数值对齐复杂**：INT8 量化的舍入模式影响对拍
   - 已处理：torch 侧 `round()` 是 round-half-to-even，与 Triton 默认一致；
     对拍 12 组全通过，relerr 与 tile 配置无关（说明没有配置相关的错误）
5. **WxA16 迁移引入回归**：移动文件导致 import 错乱
   - 已消除：forward 重构后逐元素一致（test_moe_integration rel_err=0.00e+00
     守护），且已跑完整 WxA16 eval 验证零回归
6. ~~**P2 显存**：fp16/int8 双缓冲~~ → 已消除：分派否决后只存 int8 一份；
   旋转+量化融合 kernel 同时消除了 fp32 中间态（两段式 per-forward 峰值
   约为 4.5x 激活大小）
7. **JIT 编译污染测量**（🆕 端到端阶段新发现）：首次 wxa8 eval 逐 expert
   形状边跑边编译，端到端可虚增 10%+（wiki 首跑 62.68s vs 重跑 54.09s）。
   - 缓解：测速前先用任意一次 wxa8 eval 捂热 Triton 磁盘缓存

## 七、仓库结构

```
quantization/
├── __init__.py
├── common/               # 公共工具（两边共用的 profile / autotune / profiler 等）
│   └── __init__.py
├── wxa16/                # WxA16 实现（从根目录移入）
│   ├── __init__.py
│   ├── bit_partitioned_moe.py
│   ├── dartmoq_backend.py
│   ├── linear.py
│   └── memory_stats.py
└── wxa8/                 # WxA8 实现（新建）
    ├── __init__.py
    ├── bit_partitioned_moe.py   # P2：复用 wxa16 的存储/加载，只换 forward
    └── linear.py                # P3：attention 路径
```

kernel 与模块分层沿用 WxA16 的既有约定 —— **模块在 `quantization/`，
Triton kernel 在 `turboquant_utils/`**：

```
turboquant_utils/
├── triton_kernels.py       # WxA16 融合 kernel（既有）
└── triton_kernels_a8.py    # WxA8 融合 kernel（P1 新增）
                            #   复用 triton_kernels 的 convert_to_group_first 等布局工具
test/
├── wxa8_common.py            # 测试公共工具：按真实量化管线构造用例
├── test_wxa8_kernel.py       # 对拍 + 切片一致性 + 性能 + SM 填充度 + 交叉点扫描
├── test_wxa8_tune.py         # INT8 tile 配置调优
├── test_wxa8_dot_spike.py    # 可行性 spike（裸 dot 上限 / dequant 拆解 / attention 形状）
├── test_wxa8_fused_quant.py  # rotate+quantize 融合 kernel 对拍 + 性能
├── test_wxa8_moe.py          # MoE 模块级对拍（WxA8 vs WxA16 forward）
└── test_quant_io.py          # 既有 round-trip 测试，扩展了 wxa8 加载路径检查
```

- `turboquant_utils/` 暂不迁移（等明确哪些是公共的再逐步拆）
- 主流程通过 `--inference-quant-mode wxa16 / wxa8` 切换（默认 `wxa16`）
- **权重 checkpoint 不需要分开存**：WxA8 的 packed 格式与 WxA16 完全相同，
  码本转 int8 是加载期算的（低 bit 近乎无损）。
  唯一例外是 P3 的 attention 均匀码本改造，那个需要重量化。
